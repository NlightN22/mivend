# Дизайн-концепт: портал менеджеров/операторов (`packages/manager`)

> Черновой концепт для передачи в отдельный чат для дальнейшей проработки и планирования реализации. Не является финальным техническим заданием — открытые вопросы явно помечены в конце документа.

Связанные материалы:

- GitHub issue [#25](https://github.com/NlightN22/mivend/issues/25) — первоначальная (более узкая) постановка задачи
- `docs/ai/PROJECT_CONTEXT.md`, раздел «Manager portal for discount management» — исходный драйвер approval workflow для скидок
- `AGENTS.md` — общие конвенции монорепозитория, обязательны к соблюдению при реализации

---

## 1. Контекст и цель

Сейчас вся операционная работа с заказами, товарами, ценами и клиентами ведётся либо через Vendure Admin UI (общий инструмент разработчика/технического администратора), либо не автоматизирована вовсе (согласования скидок и отсрочек — вручную, вне системы).

Нужен отдельный веб-портал для **операторов** и **менеджеров** компании — внутренний B2B backoffice, который:

1. Полностью заменяет Admin UI для всей операционной работы (заказы, клиенты, товары, цены, скидки).
2. Вводит **согласование (approval workflow)** для действий, которые сейчас никак не контролируются — в первую очередь скидки и отсрочки платежа.
3. Разграничивает видимость данных между сотрудниками: не все должны видеть всех клиентов компании.

Admin UI **не выпиливается**, а сужается до системных настроек, которые меняются крайне редко (см. раздел 5).

## 2. Персоны

| Персона                               | Кто это                                                           | Область видимости                                                                           | Особые права                                                                                                            |
| ------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Оператор**                          | Обрабатывает текущие заказы, ведёт клиентов                       | Видит **всех клиентов своего подразделения** (не только «своих»)                            | Базовые операции: заказы, карточки клиентов, стандартные цены                                                           |
| **Менеджер**                          | Ведёт закреплённых за ним клиентов                                | Видит **только своих клиентов** (их адреса, обороты, историю — скрыты от других менеджеров) | Обязан **инициировать** согласование скидок и отсрочек платежа через approval workflow (не может применить их напрямую) |
| **Согласующий (руководитель отдела)** | Например, руководитель отдела продаж, руководитель отдела закупок | Видит заявки, назначенные ему на согласование                                               | Утверждает/отклоняет заявки на своём шаге цепочки                                                                       |
| **Ген. директор**                     | Финальное звено согласования для критичных заявок                 | Видит все заявки, требующие финального утверждения                                          | Финальное утверждение/отклонение                                                                                        |
| **Администратор портала**             | Настраивает роли, права, цепочки согласования                     | Полный доступ                                                                               | Управление ролями/правами внутри портала (не путать с системными ролями Vendure в Admin UI)                             |

**Важное наблюдение из интервью с заказчиком**: видимость данных у Оператора и Менеджера устроена **обратно интуиции** — у Оператора она _шире_ (весь департамент), а у Менеджера _уже_ (только свои клиенты), при этом у Менеджера есть _эксклюзивное_ право запускать согласования. Это две независимые оси прав, не единая иерархия «оператор < менеджер < руководитель».

## 3. Модель прав доступа

### 3.1 Решение: расширяем встроенный RBAC Vendure, не строим отдельную систему

Vendure официально поддерживает регистрацию кастомных прав через `PermissionDefinition`/`CrudPermissionDefinition` (`authOptions.customPermissions`) — они работают наравне со встроенными правами, `@Allow(...)` в резолверах не отличает «наши» права от системных. Отдельную ACL-таблицу городить не нужно.

**Но:** встроенный `Permission` — это грубая двоичная модель («может/не может выполнить операцию»), она не выражает _владение данными_ («видит только своих клиентов»). Такую фильтрацию нужно делать на уровне сервиса/резолвера, аналогично уже существующему паттерну `myOrders`/`myDocuments` (фильтрация по `ctx.activeUserId` → сущность владельца). Здесь тот же принцип, но для внутреннего пользователя (Administrator), а не покупателя.

### 3.2 Новые custom field'ы (примерная схема, требует уточнения при реализации)

**Подразделение и филиал — два независимых измерения, оба нужны с самого начала (hub-spoke, решено в интервью):**

- `Administrator.customFields.departmentId` — **организационное** подразделение сотрудника (отдел продаж/закупок/СБ и т.д.) — используется прежде всего для цепочек согласования (кто на каком шаге).
- `Administrator.customFields.branchId` — id сущности `Branch` (`packages/plugins/access-control`, склад/ATP-консолидация), **не** «branch instance» из хаб-споук терминологии (docs/architecture.md) — это два не связанных друг с другом смысла слова «branch», см. docs/access-control.md's "Branch vs Department"/"Branch instance" сноски. Используется для операционной видимости заказов день-в-день — но **не** для видимости самого `Counterparty` (см. следующий абзац и docs/access-control.md's "Branch scope" — реализация ранее ошибочно фильтровала `Counterparty` по branchId, исправлено).
- `Counterparty.customFields.assignedManagerId` — менеджер, за которым закреплён клиент.

Один сотрудник может относиться к отделу продаж (`departmentId`) в конкретном филиале (`branchId`) — это ортогональные атрибуты, не одно и то же поле. Директор и СБ видят компанию через центральный хаб (без привязки к конкретному `branchId`).

**Уточнение по факту реализации, финальная версия на 2026-09-20 (расходится с исходным планом ниже)**: `departmentId` (1С-шное "Подразделение") — чисто информационное поле, **нигде и никогда не фильтрует видимость**, ни у одной сущности. Единственная реальная область видимости — `branchId` (наш, мивендовский `Branch`). Подтверждено сверкой с реальными protobuf-контрактами (`counterparty_changed.proto`/`user_changed.proto`) — 1С вообще не присылает ничего похожего на "branch", только `department_id`; заведён search-platform#140 на переименование `WarehouseChanged.branch_id`, который на самом деле тот же 1С-шный `Подразделение_Key`.

Сейчас (переходное состояние, до #65/#123/#124/#125): `Counterparty.branchId` никогда не заполняется автоматически → фильтр по нему на `Counterparty` временно вообще не применяется (иначе все увидели бы ноль клиентов). Реальный `branchId`-фильтр уже корректно работает у `Order`/`Invoice` через собственное денормализованное поле бренча (`TradingPoint.servicingBranchId`) — см. `docs/access-control.md`'s "Branch scope is the only real filtering axis" для актуального описания по сущностям. Итоговая цель (issue #123): жёсткая обязательная привязка каждого `Administrator`/`Counterparty` к `branchId`, с отдельным списком "неразобранных" для того, у кого он не проставлен — детали по каждой сущности определяются в #124 (Counterparty)/#125 (TradingPoint).

### 3.2.1 Важно: `portalRole` (существует) — это не то же самое, что роли портала менеджеров (новое)

В `plugin-counterparty` уже есть `Customer.customFields.portalRole` — это роль **контакта клиента-контрагента** внутри клиентского портала (storefront), например «может согласовывать заказы от лица компании-клиента». Это **полностью отдельная система** от ролей сотрудников нашей компании (Оператор/Менеджер/Руководитель/Директор), описанных в этом документе. Пересечения нет, но при реализации нужно явно развести именование в коде и документации, чтобы не путать «роль клиента» и «роль сотрудника».

### 3.2.2 Роли/должности сотрудников — ERP-мастер-данные с самого начала

Решено: оргструктура (подразделения, должности сотрудников) ведётся в 1С и выгружается в mivend **с первого этапа**, а не заводится вручную в портале — по аналогии с уже действующим правилом «ERP is master for business data» (external-integration-rules skill). Это новый ERP-import record type (условно `EmployeeRecord`/`DepartmentRecord`), по образцу уже существующих `CounterpartyRecord`/`OrganizationRequisitesRecord`: `erpId`, привязка к `Administrator` (по email или отдельному match-полю), `departmentId`, должность/роль. `/team` в портале в этом случае — преимущественно **просмотр** оргструктуры (аналогично тому, как каталог не редактирует базовые цены), а не полноценный CRUD; ручное администрирование в портале — только для того, что 1С не покрывает (например, привязка `assignedManagerId` к конкретным клиентам, если это не ведётся в 1С).

**Механизм лимита (черновой, отмечен заказчиком как предварительный)**: лимит самостоятельной скидки/наценки менеджера — это не процент и не абсолютная сумма, а отдельный **прайс-тип "предельная цена"**, приходящий из ERP как обычный `PriceRecord` (см. `plugin-price-entry`) — по аналогии с RETAIL/WHOLESALE. Менеджер может свободно двигать фактическую цену продажи вплоть до этого порога без согласования; ниже — только через approval workflow. Один общий механизм на всех менеджеров (не индивидуальные лимиты). Заказчик прямо отметил, что это временное решение ("возможно не лучшее"), могут пересмотреть.

**Важно**: сама числовая величина «предельной цены» **скрыта от менеджера/отдела продаж** — видна только отделу закупок и руководству. Значит серверная валидация («можно применить эту скидку без согласования / нужно согласование») должна проверять порог **на бэкенде**, не отдавая клиенту сырое значение предельной цены через API/UI менеджера — иначе конфиденциальность будет нарушена самой формой отображения (например, обратным вычислением через попытки применить разные скидки). Это требование к реализации, не просто к UI: GraphQL-поле с самим значением предельной цены не должно быть доступно роли Менеджер вообще (ни в схеме, ни в ответе), а не просто скрыто в интерфейсе.

## 4. Универсальный движок согласований (approval workflow)

### 4.1 Требование

**Важное уточнение (после дополнительного интервью): управление ценами по клиентам — это не единый механизм, а два принципиально разных, оба реализуются через approval workflow, но с разной природой заявки:**

1. **Точечная корректировка цены по конкретной заявке клиента** (`requestType: priceAdjustmentApproval`) — разовое исключение, привязанное к конкретному заказу/сделке: конкуренция в конкретной торговой точке, спецусловия, разовая акция. Не переиспользуется, не имеет срока действия — применяется один раз к одной сделке. Цепочка: Руководитель отдела продаж (инициирующий менеджер) → Руководитель отдела закупок (проверяет маржинальность и обоснованность) → Ген. директор. Возможное расширение цепочки — руководитель B2B и руководитель B2C как дополнительные шаги.
2. **Установки скидок** (`requestType: discountGrantApproval`) — действующая **политика** скидки на клиента (или клиентов) по конкретным товарным группам, с периодом действия, обоснованием и целями предоставления. Это **та же сущность `DiscountRule`**, что уже есть в коде (`plugin-price-entry`, весовые/суммовые тиеры — сейчас сеедится напрямую через `erp-import` для dev/теста, см. `PROJECT_CONTEXT.md`) — просто теперь создание/продление реальной скидки идёт через approval workflow, а не напрямую. Использует **ту же цепочку согласования**, что и точечная корректировка (закупки → директор), так как заявка тоже проверяется на маржинальность/обоснованность.
3. **Отсрочка платежа** (`requestType: creditTermApproval`) — отдельная цепочка ролей, состав которой может отличаться от ценовых сценариев.

Заказчик прямо обозначил: **цепочка ролей для разных типов заявок разная** — то есть нужен не хардкод одного сценария, а настраиваемый универсальный механизм. `priceAdjustmentApproval` и `discountGrantApproval` в данный момент используют одинаковую цепочку, но остаются **разными `requestType`** в движке, потому что различаются по природе заявки (разовая vs действующая политика с продлением) и по структуре `payload`.

### 4.1.1 Критический разбор механизма «Установки скидок» (продление) — принятые решения

По итогам критической оценки текущей практики (продление = создание новой скидки на основе старой, действующей через фиксированный период) — заказчик подтвердил, что механизм в целом правильный (защита от «скидка продлевается вечно без реального пересмотра» — это осознанная практика, не баг), но требует четырёх усилений, принятых в концепт:

1. **Связь с историей.** Новая заявка на продление обязана ссылаться на скидку, которую она продлевает (`supersedesDiscountRuleId`). Согласующий должен видеть **всю цепочку продлений** данной скидки на экране заявки, а не только текущую заявку в изоляции — иначе согласование вырождается в формальность.
2. **Обязательное новое обоснование.** При продлении заявка предзаполняется данными старой скидки (чтобы не печатать всё заново), но **поле "обоснование" не может быть пустым или сохранённым без изменений от предыдущей заявки** — заказчик должен явно сформулировать, почему скидка продлевается на этот раз. (Технически: не пытаться алгоритмически детектировать «текст не изменился» — это ненадёжно для свободного текста; вместо этого показывать согласующему прошлое и новое обоснование рядом, полагаясь на человеческую проверку, а не на автоматическую валидацию содержимого.)
3. **Grace period при истечении.** Скидка не должна тихо обрываться в день истечения без предупреждения клиенту/менеджеру — нужен явный период после уведомления, в течение которого скидка ещё действует, пока идёт продление, плюс повторные напоминания менеджеру (не одно уведомление и тишина). Точный срок grace period — на этап технической проработки.
4. **Эскалация при N-м подряд продлении без изменений условий.** Если скидка продлевается несколько раз подряд с одинаковыми параметрами (без пересмотра процента/условий) — это сигнал, что она уже не «временное исключение», а фактически постоянная цена, которую нужно было бы завести иначе. При достижении порога N — принудительная эскалация на более высокий уровень цепочки (например, сразу к ген. директору, минуя обычный порядок), а не тихое повторное согласование по обычной цепочке. Точное значение N — предмет отдельного решения при реализации.

### 4.2 Рекомендация по технологии (по итогам исследования)

Изучены варианты:

- **Тяжёлые оркестраторы (Temporal.io, Camunda/Zeebe, Conductor)** — избыточны для этой задачи. Рассчитаны на durable execution в масштабе (высоконагруженные, долгоживущие процессы), требуют отдельного сервиса/кластера в эксплуатации. Для нескольких типов заявок и низкой частоты (единицы-десятки заявок в день) — операционные издержки не окупаются.
- **Готовые npm-пакеты уровня NestJS** (`@jescrich/nestjs-workflow`, `nestjs-temporal-core` и подобные) — нишевые, без признаков широкого использования/поддержки. Большинство реальных проектов в этой нише пишут своё решение, и это не случайность.
- **XState** — зрелая, хорошо поддерживаемая библиотека state-machine. Готового шаблона «approval workflow на XState» в открытом доступе нет, но паттерн «внешняя система/человек согласовывает → отправляется событие → машина состояний переходит на следующий шаг» — это ровно документированный XState-сценарий «human-in-the-loop». Сама по себе XState не хранит состояние — персистентность всё равно реализуется через Postgres/TypeORM.

**Рекомендация: гибрид.** XState — для логики переходов состояний (запускается из декларативного описания цепочки шагов на конкретный тип заявки), TypeORM-сущности — для хранения и аудита в Postgres. Это даёт «готовую библиотеку» именно там, где она реально полезна (корректность графа состояний, готовые edge-cases), не требуя разворачивать отдельный сервис.

**Проверено против реальных цифр заказчика (сейчас ~257 согласований/день по всем сотрудникам в 1С, ожидается рост).** Это не аргумент в пользу Temporal: 257/день — это ~1 заявка раз в 5-6 минут в рабочее время, статистически незначимая нагрузка для Postgres (который свободно держит тысячи транзакций в секунду). Ключевой вопрос был не throughput, а **природа шагов**: подтверждено, что все шаги — решение человека («согласовано»/«отказано» + комментарий), без автоматических шагов, которые звонят во внешние системы (1С, склад, банк) и ждут ответа с ретраями. Именно вторая ситуация — та, где Temporal/Camunda реально окупаются (durable execution, retry/compensation через границы сервисов). Здесь её нет — гибрид XState+Postgres остаётся правильным выбором независимо от объёма и разнообразия типов цепочек (разнообразие решается конфигурацией `WorkflowDefinition`, не инфраструктурой оркестратора).

### 4.3 Решённые по итогам интервью детали поведения

- **Шаги — последовательные, без автоматического параллелизма в MVP.** Обсуждённый сценарий с СБ (см. ниже) — это не параллельный шаг, а **ручная эскалация**, отдельный механизм.
- **Ручная эскалация шага**: если согласующий на текущем шаге долго не реагирует (например, служба безопасности), **инициатор заявки** может вручную эскалировать шаг — но только на роль/сотрудника **из заранее определённого в конфигурации цепочки списка вышестоящих** (не любому человеку). Эскалированный вышестоящий проводит шаг сам. **Без автоматического таймаута** в MVP — эскалация только по ручному решению инициатора, никакого фонового планировщика/крона не нужно.
- **Отклонение на любом шаге — терминально.** Заявка сразу переходит в статус `rejected`, доработка невозможна. Если условия нужно пересмотреть — инициатор создаёт новую заявку с нуля (версионирование заявок не требуется).
- **Уведомления — MVP: только in-app инбокс** (`/approvals`), без email/эскалации по времени. Интеграция с внешним сервисом уведомлений — отдельная задача на будущее, в MVP не входит.
- **Хранение истории — без архивации.** Все `ApprovalRequest`/`ApprovalStep` остаются в основных таблицах навсегда, ротация/архивация не проектируется для MVP (ожидаемый объём — единицы-десятки заявок в день, годами не станет проблемой для Postgres).

### 4.4 Примерная модель данных (черновик)

**Формат `WorkflowDefinition` — простой JSON, не BPMN** (решено после сравнения с `bpmn-js`/BPMN XML — см. исследование выше: готового «Swagger-style» авто-рендерера для JSON нет, но при таком масштабе цепочек — единицы шагов, только последовательные — самописный конвертер JSON→Mermaid размером в несколько десятков строк не является «изобретением велосипеда»; тащить ради этого формат BPMN XML избыточно). Хранится в Postgres (например, одна строка/JSON-колонка на `requestType`, редактируется через `/settings`), не в коде плагина.

Пример конкретного конфига для цепочки «Скидка/наценка сверх лимита» (см. диаграмму в 4.6):

```json
{
    "requestType": "priceAdjustmentApproval",
    "displayName": "Скидка/наценка сверх предельной цены",
    "steps": [
        {
            "order": 1,
            "role": "SalesDeptHead",
            "requiredPermission": "ApproveDiscountRequest",
            "escalatesTo": ["GeneralDirector"]
        },
        {
            "order": 2,
            "role": "PurchasingDeptHead",
            "requiredPermission": "ApproveDiscountRequest",
            "escalatesTo": ["GeneralDirector"]
        },
        {
            "order": 3,
            "role": "GeneralDirector",
            "requiredPermission": "ApproveDiscountRequest",
            "escalatesTo": []
        }
    ]
}
```

Пример для иллюстративной цепочки «Лимит через СБ» (см. 4.6):

```json
{
    "requestType": "securityLimitApproval",
    "displayName": "Согласование лимита через СБ",
    "steps": [
        {
            "order": 1,
            "role": "SecurityOfficer",
            "requiredPermission": "ApproveSecurityLimit",
            "escalatesTo": ["SalesDirector", "GeneralDirector"]
        }
    ]
}
```

Именно из этой JSON-структуры на старте плагина строится реальная XState-машина (шаги → состояния, `escalatesTo` → дополнительные переходы из того же состояния) — и из неё же самописный конвертер рендерит Mermaid-диаграмму для `/settings` (см. 4.6), так что диаграмма никогда не расходится с реальной конфигурацией, потому что генерируется из неё, а не поддерживается вручную отдельно.

`discountGrantApproval` использует ту же цепочку, что `priceAdjustmentApproval` (см. 4.1) — тот же `WorkflowDefinition`, что и в первом примере выше, но другой `requestType` и другая структура `payload` (см. пример `ApprovalRequest.payload` ниже — с полем `supersedesDiscountRuleId` для связи с историей продлений, см. 4.1.1).

Пример `payload` заявки на продление скидки (внутри `ApprovalRequest`, не отдельная таблица):

```json
{
    "counterpartyErpId": "cnt-001",
    "facetValueCode": "brand-acme",
    "percent": 7,
    "validFrom": "2026-08-01T00:00:00.000Z",
    "validTo": "2026-11-01T00:00:00.000Z",
    "justification": "Продление на Q4 в связи с сохранением объёма закупок клиента на уровне Q3",
    "supersedesDiscountRuleId": "dr-2026-Q3-cnt001-acme"
}
```

ApprovalRequest (сущность нового плагина, например packages/plugins/approval-workflow)

- id, type, payload (JSON — снимок того, что согласовывается: скидка/условия; для `discountGrantApproval` включает `supersedesDiscountRuleId`, см. пример выше)
- status: 'pending' | 'approved' | 'rejected' | 'cancelled'
- currentStepIndex
- requestedByAdministratorId
- createdAt / decidedAt

ApprovalStep (аудиторский след по каждому шагу)

- approvalRequestId, stepIndex, requiredRole
- approverAdministratorId (nullable, пока не решено)
- wasEscalated: boolean, escalatedByAdministratorId (nullable) — фиксирует факт и инициатора эскалации
- decision: 'approved' | 'rejected' | null
- comment, decidedAt

````

Точная схема — предмет отдельной технической проработки, это лишь иллюстрация принципа.

### 4.5 Универсальный «Инбокс согласований»

Раз движок универсальный — в портале должен быть отдельный сквозной раздел «Согласования» (не спрятанный внутри «Скидок»), показывающий согласующему **все** назначенные ему заявки, независимо от типа. Это первый по важности новый раздел портала помимо базового CRUD.

### 4.6 Нотация для фиксации цепочек (best practice)

Три подхода, обычно комбинируются:

1. **BPMN** — формальный индустриальный стандарт: swimlane на роль, gateway на условия, явные ветки эскалации/отказа. Инструмент — Camunda Modeler или draw.io/diagrams.net (используется только как рисовалка, без разворачивания самого движка Camunda). Уместен, если схему нужно показывать нетехническим стейкхолдерам как формальный документ.
2. **Mermaid-диаграммы прямо в Markdown** — текстовые, версионируются вместе с кодом в git, рендерятся нативно в GitHub/VS Code без экспорта картинок. Визуально близки к тому, как мыслит сам XState (граф состояний/переходов), выбранный для движка (см. 4.2). **Рекомендация для этого проекта** — основной формат ниже.
3. **Табличная форма** (шаг × роль × условие × эскалация) — менее наглядно, но точнее по деталям, ближе к самому конфигу `WorkflowDefinition`. Используется вместе с диаграммой, не вместо.

**Решено (после отдельного исследования): диаграммы в `/settings` генерируются программно из реального `WorkflowDefinition` (см. 4.4), не поддерживаются вручную.** Рассматривали `bpmn-js` (готовый read-only рендерер BPMN-диаграмм, `Viewer`-класс, никакого движка Camunda разворачивать не нужно) — это единственный по-настоящему готовый инструмент такого рода, но требует хранить конфиг как BPMN XML вместо простого JSON. Для наших коротких линейных цепочек это несоразмерная плата за формат; выбран **простой JSON + самописный конвертер JSON→Mermaid** (десятки строк кода) — при таком масштабе цепочек это не «изобретение велосипеда» в смысле избегания которого предостерегает YAGNI, готового полноценного «колеса» для этой узкой задачи в принципе не существует. Диаграммы ниже в этом документе — иллюстрация того, что получится, но в реализации не поддерживаются руками отдельно от кода.

#### Пример: цепочка «Скидка/наценка сверх лимита»

```mermaid
stateDiagram-v2
    [*] --> Draft: Менеджер создаёт заявку (цена ниже предельной)
    Draft --> SalesHeadReview: отправлена

    SalesHeadReview --> PurchasingHeadReview: согласовано
    SalesHeadReview --> Rejected: отклонено
    SalesHeadReview --> SalesHeadReview: эскалация (инициатор → вышестоящий из escalatesTo)

    PurchasingHeadReview --> DirectorReview: согласовано
    PurchasingHeadReview --> Rejected: отклонено
    PurchasingHeadReview --> PurchasingHeadReview: эскалация

    DirectorReview --> Approved: согласовано
    DirectorReview --> Rejected: отклонено

    Approved --> [*]: цена применяется к заказу
    Rejected --> [*]: заявка закрыта, доработка = новая заявка
````

| Шаг | Ответственный               | Условие перехода          | При согласовании             | При отказе              | Эскалация                                           |
| --- | --------------------------- | ------------------------- | ---------------------------- | ----------------------- | --------------------------------------------------- |
| 1   | Руководитель отдела продаж  | Заявка создана менеджером | → шаг 2                      | `Rejected`, терминально | Вышестоящий из `escalatesTo` (конфигурация цепочки) |
| 2   | Руководитель отдела закупок | Шаг 1 согласован          | → шаг 3                      | `Rejected`, терминально | Аналогично                                          |
| 3   | Ген. директор               | Шаг 2 согласован          | `Approved`, цена применяется | `Rejected`, терминально | — (последний шаг)                                   |

#### Пример: цепочка «Согласование лимита через СБ» (иллюстрация механизма эскалации)

```mermaid
stateDiagram-v2
    [*] --> SecurityReview: заявка создана
    SecurityReview --> Approved: СБ согласовало
    SecurityReview --> Rejected: СБ отклонило
    SecurityReview --> ExecutiveOverride: инициатор эскалировал (СБ долго не отвечает)
    ExecutiveOverride --> Approved: вышестоящий провёл шаг сам
    ExecutiveOverride --> Rejected: вышестоящий отклонил
    Approved --> [*]
    Rejected --> [*]
```

Это дублирует ту же механику эскалации, что и в первом примере — приведено отдельно, чтобы визуально показать, что эскалация **не создаёт новый параллельный шаг**, а замещает исполнителя на текущем шаге.

Обе диаграммы — иллюстрация принципа на основе известных сегодня деталей, не финальная спецификация. Цепочка «Отсрочка платежа» пока не имеет подтверждённого состава ролей (см. 8.2) — её диаграмма будет добавлена после уточнения.

### 5.1 Дашборд по роли

- **Оператор**: метрики по подразделению — заказы в работе, просроченные, новые клиенты.
- **Менеджер**: метрики по своим клиентам — активные заказы, статус поданных на согласование заявок.
- **Руководитель/директор**: сводка по компании/отделу + счётчик заявок, ожидающих _его_ решения (прямая ссылка на `/approvals`).

## 6. Технологический стек (по аналогии со storefront)

- Отдельное Vue 3 + Vite SPA приложение в `packages/manager/`, тот же паттерн, что `packages/storefront/`.
- API: Vendure **Admin API** (`/admin-api`), не Shop API.
- Аутентификация: сессия администратора (bearer/cookie), отдельная от клиентской сессии Shop API.
- UI: переиспользование `packages/ui-kit/` — без отдельной дизайн-системы (`Mv*`-компоненты).
- GraphQL-операции — только через codegen (`.graphql`-файлы рядом со страницами), без ручных строковых запросов — по аналогии со storefront.
- Стейт-менеджмент: свои Pinia-стораы, без общего состояния со storefront.
- Approval workflow — новый плагин `packages/plugins/approval-workflow` (или похожее имя), owns `ApprovalRequest`/`ApprovalStep`, экспортирует сервис для других плагинов (discount-rule, credit-terms) через стандартный `imports`/`exports` паттерн (см. backend-plugin-rules skill, «Inter-plugin communication»).

---

## 7. Граница с Vendure Admin UI

Admin UI остаётся **только** для системных настроек, которые задаются один раз при деплое и почти никогда не меняются:

- Каналы (Channels)
- Валюты
- Налоговые зоны
- Способы доставки/оплаты (конфигурация методов, не сами транзакции)
- Системные роли/права уровня Vendure (не путать с ролями портала — оператор/менеджер/руководитель — которые управляются в `/team` нового портала)

Всё операционное (заказы, товары, цены, клиенты, скидки, документы) — полностью переезжает в новый портал.

## 8. Открытые вопросы

### 8.1 Решено в ходе интервью

- ~~Параллельные шаги согласования~~ — не нужны в MVP; сценарий «согласование СБ, которое можно провести самому» реализуется через **ручную эскалацию** (см. 4.3), не через истинный параллелизм.
- ~~Отклонение на промежуточном шаге~~ — заявка сразу закрывается (`rejected`), доработка = новая заявка.
- ~~Уведомления~~ — MVP: только in-app инбокс `/approvals`, без email/эскалации по времени. Внешний сервис уведомлений — отдельная будущая задача.
- ~~Глубина хранения истории~~ — без архивации, всё хранится в основных таблицах навсегда.
- ~~Связь `portalRole` с ролями портала менеджеров~~ — подтверждено: это полностью разные системы (см. 3.2.1).
- ~~Готовность 1С отдавать оргструктуру~~ — да, ведём как ERP-мастер-данные с первого этапа, новый ERP-import record type по образцу `CounterpartyRecord` (см. 3.2.2). `/team` в портале — преимущественно просмотр, не полноценный CRUD.
- ~~Механика эскалации~~ — инициатор заявки вручную выбирает, кому эскалировать, но только из заранее заданного в конфигурации цепочки списка вышестоящих ролей. Без автоматического таймаута.
- ~~Технология approval-движка~~ — гибрид XState (переходы состояний) + TypeORM-сущности (хранение/аудит), без внешних оркестраторов (см. 4.2).
- ~~Редактирование базовых цен в портале~~ — не нужно, базовые цены по типам остаются мастер-данными ERP. В портале — только просмотр + отдельный инструмент точечной скидки/наценки в рамках лимита (см. 3.3, "Каталог и цены").
- ~~Общий/раздельный каталог по подразделениям~~ — ассортимент товаров общий на всю компанию; разными для разных ролей могут быть только видимые **типы цен** (например, отдел продаж не видит закупочную цену).
- ~~Видимость заказов для директора/СБ~~ — директор видит все заказы компании через центральный хаб, СБ — тоже все; руководители отделов — только заказы своего отдела.
- ~~Видимость клиентов у руководителя отдела~~ — только клиенты своего отдела, симметрично заказам (см. 3.3).
- ~~Механизм лимита скидки/наценки~~ — отдельный ERP-мастер прайс-тип «предельная цена» (не процент/сумма), общий на всех менеджеров. Отмечено заказчиком как предварительное решение, возможен пересмотр (см. 3.3).
- ~~Справочник "тип цены → какие роли его видят"~~ — закупочная/себестоимость вообще не выгружается из 1С в mivend; «предельная цена» выгружается, но видна только отделу закупок и руководству — требует технической защиты на уровне GraphQL-схемы, не только UI (см. важное примечание в 3.3).
- ~~Кто редактирует список ролей для эскалации~~ — только Администратор портала (`ManageApprovalWorkflows`), настройка цепочек и `escalatesTo` — системная конфигурация, не операционное действие руководителя отдела.
- ~~Стратегия наполнения e2e~~ — параллельно с каждым разделом по мере реализации (как в storefront), не отдельным этапом в конце.
- ~~Многофилиальность (hub-spoke)~~ — решено закладывать branch-контекст **сразу**, не откладывать на Phase 2 (в отличие от первоначальной постановки в issue #25). Подразделение (`departmentId`) и филиал (`branchId`) — два независимых измерения на `Administrator` (см. 3.2): первое определяет цепочку согласования, второе — операционную видимость заказов/клиентов день-в-день. Директор/СБ видят компанию через центральный хаб без привязки к конкретному `branchId`.
- ~~Формат конфига цепочек и способ визуализации~~ — простой JSON (не BPMN), диаграмма/таблица в `/settings` генерируется программно самописным JSON→Mermaid конвертером из реального `WorkflowDefinition` (см. 4.4/4.6), не поддерживается вручную.
- ~~Механизм «Установки скидок» (продление)~~ — критически пересмотрен и уточнён (см. 4.1.1): связь с историей продлений (`supersedesDiscountRuleId`), обязательное новое обоснование при продлении, grace period при истечении, эскалация при N-м подряд продлении без изменений условий. Подтверждено: это та же сущность `DiscountRule`, что уже в коде, и та же цепочка согласования (закупки → директор), что и точечная корректировка цены — но отдельный `requestType` (`discountGrantApproval` vs `priceAdjustmentApproval`), так как различаются по природе заявки (разовая vs действующая политика).
- ~~Полный список custom permissions по всем экранам~~ — закрыт для всех разделов портала, включая `/team`, `/settings`, `/documents` (см. таблицы в 3.3). `ReassignCounterpartyManager` — Администратор портала и Руководитель отдела продаж (в рамках своего отдела); видимость `/documents` наследуется от видимости клиента, отдельного права не требуется; `GenerateContract` совпадает по объёму с правом видеть клиента.
- ~~Где создаётся заказ и где применяется корректировка цены~~ — исходно упущено в первом варианте структуры портала. Добавлена страница `/orders/new` (создание заказа от лица клиента — основная повседневная работа Оператора: приём звонков клиентов и ручной ввод заказов). Отдельная страница `/pricing` убрана — заказчик справедливо указал, что корректировка цены имеет смысл только в контексте конкретного, уже открытого заказа; инструмент встроен прямо в строку товара на `/orders/new` и `/orders/:code` (см. раздел 5).
- ~~Сверка со сторонним списком разделов (второе мнение от другой модели)~~ — прогнали независимо предложенный список разделов через критику. Реально стоящие добавления (уже подкреплены существующим кодом, не гипотезы): кросс-ссылки/применимость по OEM на карточке товара и поиск по VIN/OEM в каталоге и при создании заказа (`plugin-cross-reference`/ES-поиск уже реализованы) — добавлены в `06-catalog-list.md`/`07-product-detail.md`/`02b-order-create.md`. Также добавлена простая страница `/profile` (личные настройки). Явно лишнее (дублирует уже спроектированное иначе): отдельная страница "Корзина" (это и есть таблица строк на `/orders/new`), "Справочники" (уже в карточке клиента), общий "Центр уведомлений" (уже решено — `/approvals`-инбокс + отложенный сервис уведомлений). Отложено с отдельными issue: коммерческие предложения — issue [#30](https://github.com/NlightN22/mivend/issues/30) (редкий этап, только B2B-менеджеры с конечными потребителями); сводная финансовая страница по всем клиентам — issue [#31](https://github.com/NlightN22/mivend/issues/31) (пока — синк дебиторки из ERP, без отдельной страницы). Отчёты (продажи/KPI/ABC) — заказчик решил, что пока достаточно сводки на дашборде, отдельного issue не заводили. Отгрузки/логистика — не нужны в этом портале, статусы заказов уже покрываются существующим полем статуса заказа (`plugin-erp-order`), склад — не персонаж этого портала.

### 8.2 Остаются открытыми (требуют решения на этапе технического планирования)

1. **Точная длительность grace period** при истечении скидки (см. 4.1.1, п.3) — не определена, оставлена на техническую проработку.
2. **Точное значение N** для эскалации при подряд идущих продлениях без изменений (см. 4.1.1, п.4) — не определено.

## 9. Предлагаемая последовательность реализации (для обсуждения)

1. Скелет портала: `packages/manager/`, аутентификация через Admin API, базовый layout, переиспользование ui-kit.

ERP-import для оргструктуры (новый record type, условно `EmployeeRecord`/`DepartmentRecord`, включающий `departmentId` и `branchId` — см. 3.2/3.2.2) + custom permissions в Vendure (`PermissionDefinition`) + фильтрация видимости клиентов/заказов на уровне сервиса по обоим измерениям (own/department/branch/all).

7. `/documents`, `/team` (в основном просмотр оргструктуры из ERP), `/settings`.
